SpaceEngine on Apple Silicon

I got the Steam release of SpaceEngine running natively on an Apple Silicon Mac, as a personal experiment. Here is what worked, what macOS gets in the way of, and what I learned that might help an official Mac version.

Game 0.991, build 50.2155 (Steam) Mac MacBook Air, Apple M5, 32 GB OS macOS 27 Date October 2026

Why I'm writing

Wine and CrossOver can't run SpaceEngine on a Mac because the game needs more OpenGL than macOS provides, and Boot Camp is gone on Apple Silicon. I wanted to see whether a native build was feasible at all. It is: the game boots, renders at full Retina resolution at 60 frames per second on a fanless laptop, and I've spent hours flying around the planetarium.

I made this from my own purchased copy, for my own use only. Nothing from the game has been or will be shared: no executable, no translated code, no data, and the encrypted .pak archives were never opened outside the game itself. Steam's ownership checks run normally. I'm writing because the technical findings below are probably more useful to you than to me, and to ask whether a Mac version is something you'd consider.

Findings for a native Mac build

These are the places where macOS behaved differently from Windows drivers. Each one stopped something from working until it was handled.

  1. OpenGL stops at 4.1, and a few 4.2+ features are used

    The engine runs on 4.1 once the version check is waived. Beyond 4.1 it relies on GL_ARB_buffer_storage (persistently mapped uniform buffers, and pixel-pack buffers for frame capture) and calls glReadnPixels (4.5) when recording video. Reverse-Z depth (glClipControl) and direct state access are unavailable, and the existing fallbacks work.

    What worked: persistent mappings backed by ordinary memory, uploaded before each draw and filled after each pixel read; glReadnPixels mapped to glReadPixels.

  2. Apple doesn't list extensions that became core

    Capabilities are decided by extension name through GLEW. Apple's core profile reports only a short list, so GL_EXT_texture3D and GL_EXT_framebuffer_multisample appear missing even though 3D textures and multisampling are core. Without the first, the atmosphere model cache refuses to initialise and every body reports an unknown atmosphere model. GLEW also only loads glReadnPixels when 4.5 or GL_KHR_robustness is present, yet the recorder calls it unconditionally.

    Suggestion: test the GL version for features that are core in it, rather than the old extension names.

  3. Program binaries are "supported" with zero formats

    Apple's 4.1 includes glProgramBinary but reports GL_NUM_PROGRAM_BINARY_FORMATS as 0. If the shader cache trusts the extension, the first run works and every later run draws a black screen, because no cached program can be loaded back.

    Suggestion: enable the cache only when at least one binary format is reported.

  4. Apple's GLSL compiler is strictly 4.10

    45 shaders needed at least one change and 4 programs failed to link. Each problem is a construct other vendors accept:

    • #if on a name that was never defined is an error rather than 0.
    • An interpolation qualifier must come before in/out.
    • const with a run-time initializer and stray semicolons after function bodies are 4.20 features.
    • texture2D and similar 1.20 names don't exist in the core profile.
    • A variable named like a struct type is parsed as the type, so name.field is a syntax error.
    • Stage interfaces are paired by name, not by layout(location): a vertex out and a geometry in with different names don't link (orbit lines).
    • Two active vertex attributes at the same location are a link error (cube-map orbits).

    Suggestion: compiling the shader set once with Apple's compiler, or with a strict validator such as glslang at version 410, would catch all of these.

  5. Contexts and threads

    Loader-thread contexts that share objects with the main context work well, as long as only the main thread uses the window's drawable. Contexts on other threads should be made current without one.

  6. Retina displays

    The engine thinks in pixels throughout, which suits macOS. The window just needs a high-density backing store, with sizes and mouse positions converted from points at the boundary. Rendering at native resolution held 60 fps in my tests.

  7. Mac keyboards

    Modifier shortcuts work once left and right Shift, Ctrl and Alt are tracked separately, as the engine checks them per side. Laptop keyboards have no numeric keypad, and Home, End, Page Up, Page Down, forward Delete and F1–F12 all need the fn key. Many default bindings use those keys. Mac users also expect Cmd where Windows uses Ctrl.

    Suggestion: a Mac default key map, or Cmd accepted as Ctrl.

  8. Video encoders

    LGPL FFmpeg 8 builds cleanly for arm64, and SVT-AV1 runs well on Apple Silicon. NVENC, AMF and QSV don't exist on a Mac, but Apple's VideoToolbox encoders (H.264, HEVC, ProRes) are hardware-accelerated and LGPL-compatible. They would be the natural Mac counterpart if they were added to the encoder list.

  9. Steam needs nothing special

    Valve's macOS Steamworks library is arm64-native and initialises app 314650 for a native process; ownership, interfaces and Workshop queries all work.

How I did it

I don't have your source, so I translated the shipped Windows executable instead. Each x86-64 function was converted mechanically to C and compiled for arm64, then checked instruction by instruction against the original in an emulator. A small layer stands in for the parts of Windows the game uses: windows, files, threads, OpenGL contexts, SDL and FFmpeg. It's a working proof of concept, but it's tied to this exact build and can't be distributed, so it isn't a substitute for a real port.

Long-term caveat. Apple deprecated OpenGL in 2018. It still works well on macOS 27, but a lasting Mac version would probably move to Metal, or to Vulkan through a Metal translation layer.
